# Bumper Bay 클래스 구조 리빌드안 (2026-10-17)

현재 프로젝트(FallGuys_Sample)와 같은 기능을 상속 구조로 다시 만들 때의 설계안입니다.
프로토타입으로 검증하기 전의 **제안**이며, 아래 5번의 불확실한 항목은 아직 확인되지 않았습니다.

## 1. 핵심 원칙
1. **상속은 "무엇인가"에만 쓴다**: 장애물은 모두 `움직이는 프롭`이고, 움직임 방식(회전·왕복 등)만 자식 클래스로 나눈다.
2. **나머지는 부품을 끼워 쓴다**: "닿는 모양", "미는 방향"은 별도 부품 클래스로 만들어 장애물에 끼운다.
3. **공통 일은 한 곳에서 한 번만 한다**: 플레이어 위치 읽기, 튕김 실행, 소리 재생은 서비스 장치가 맡는다. 장애물마다 복사하지 않는다.

## 2. 장애물 클래스 구조 (2강)
```
creative_device
└─ movable_prop (추상 부모)   프롭 하나, 시작 위치 저장, 이동 시간·딜레이·1회/복귀 옵션,
   │                         난이도 옵션(속도 배율, 튕김 세기), Setup()과 반복 루프 뼈대
   ├─ rotating_prop          연속 회전: 프로펠러, 회전 통나무, 회전 봉
   ├─ translating_prop       왕복 이동: 주먹, 슬라이딩 벽, 셔틀 발판
   ├─ scaling_prop           크기 변화: 사라지는 타일
   └─ animating_prop         위치+회전 동시: 플리퍼 스윙, 시계추
      ├─ seesaw_prop         시소(기울기)
      └─ orbiting_prop       시소 위 범퍼 기둥(공전)

hazard_shape (닿는 모양, 부품)   disc_shape / capsule_shape / box_shape
push_rule (미는 방향, 부품)      radial_push(바깥으로) / fixed_push(고정 방향) /
                                tangent_push(회전 접선) / velocity_blend_push(이동 방향 섞기)
```
현재 장애물의 표현:
- 플리퍼 = `animating_prop` + `capsule_shape` + `tangent_push`
- 주먹 = `translating_prop` + `box_shape` + `fixed_push`
- 시소 기둥 = `orbiting_prop` + `capsule_shape` + `velocity_blend_push`

서비스 장치 3개:
- `player_tracker`: 틱마다 플레이어 위치를 한 번만 읽어 모두에게 제공 (지금의 `RefreshSnaps`, `common_types.verse`의 `player_snap`)
- `knockback_service`: 바운서 풀, 쿨다운, 튕김 실행, 소리 (지금 `flipper_knockback`, `seesaw_controller`에 중복된 `TryKnockback`, `RunKnockback`, `PlaySfxAt`)
- `hazard_manager`: 장애물 전체를 한 번의 루프로 판정

배열 연결 문제 해결: **장애물 하나당 장치 하나**를 놓고 `@editable` 칸은 프롭 하나뿐이다. 매니저는 **태그로 자동 수집**하므로 배열이 필요 없다 (MCP로 배열 참조를 만들 수 없는 제약 회피).

## 3. 게임 흐름 클래스 구조 (3강)
```
match_manager (장치)            라운드 시작·종료 총괄 (지금 race_manager의 흐름 부분)
├ racer_state (구조체)          플레이어 한 명의 상태: 체크포인트 수, 골인 순위, 걸린 시간
│                               (지금은 맵 5개로 분산: FinishedRank, FinishedSpent, CheckpointCount ...)
├ checkpoint_tracker (장치)     체크포인트 집계 → CheckpointEvent
├ finish_line (장치)            골인 감지 → FinishedEvent
├ ranking (클래스)              순위 계산만 하는 순수 로직 (지금의 RankOf)
├ race_hud (장치) + result_screen + glyph_text   화면 표시
├ audio_director (장치)         music_player + sfx_player: Play(음원 종류, 플레이어) 한 곳에서
└ minimap_markers (장치)        지금의 minimap_manager
```
장치끼리는 직접 호출하지 않고 **이벤트(`event(player)`)로 연결**한다. HUD와 소리는 `FinishedEvent`, `CheckpointEvent`를 구독만 한다.

## 4. 요청 순서 (연습 및 녹화용)
한 단계 = 만들기 → 빌드 → 확인 → 다음. 앞 단계가 확인되어야 넘어간다.

| 단계 | 요청 내용 | 확인 방법 |
|---|---|---|
| 0 | 준비: `proto_` 접두사 파일, `Test_Inheritance` 폴더, 구조도 문서 | 구조도 확인 |
| 1 | `player_tracker` (위치 서비스) | 로그에 위치 출력 |
| 2 | `knockback_service` (바운서 풀, 쿨다운) | 테스트로 튕김 1회 |
| 3 | `movable_prop` (추상 부모) + `rotating_prop` 프로펠러 1개 | 에디터에서 회전 확인 |
| 4 | `hazard_shape`, `push_rule` 부품 + 프로펠러에 튕김 연결 | 플레이로 튕김 |
| 5 | `translating_prop` (주먹), `animating_prop` (플리퍼) 추가 | 자식 클래스만 추가해 동작 |
| 6 | 태그 자동 수집 (`hazard_manager`) | 장애물 4종이 배열 연결 없이 동작 |
| 7 | `seesaw_prop` + `orbiting_prop` | 시소 기울기와 기둥 공전 |
| 8 | `racer_state`, `checkpoint_tracker`, `finish_line` (이벤트) | 로그로 이벤트 확인 |
| 9 | `race_hud`, `result_screen` | 화면 확인 |
| 10 | `audio_director` | 소리 확인 |
| 11 | 통합 테스트, 정리 (삭제 또는 보관 결정) | 현재 게임과 기능 비교 |

- 2강 녹화 구간: 1~7단계 / 3강 녹화 구간: 8~11단계

요청 문장 틀:
> "(단계 N) `클래스이름`을 만들어 줘. 부모는 `부모클래스`이고, 편집 가능한 옵션은 `옵션들`이야. `proto_` 접두사 파일로 만들고, 만든 뒤 빌드와 [확인 방법]까지 해 줘."

## 5. 아직 확인하지 못한 것 (프로토타입으로 검증)
- 추상 부모 클래스의 `@editable` 옵션이 자식 장치의 Details 패널에 그대로 보이는지
- 태그 자동 수집(`FindCreativeObjectsWithTag`)이 이 프로젝트에서 동작하는지
- "한 번의 루프로 모든 장애물 판정"이 지금 방식보다 가벼운지 (성능 미측정)
- 부품 클래스(`hazard_shape`, `push_rule`)를 `@editable`로 장치에서 고를 수 있는지, 코드 조립만 가능한지
- 하나라도 안 되면 구조를 단순화한다 (예: 부품 대신 부모 클래스 옵션 값으로 처리).

## 6. 프로토타입 안전 규칙
- 시작 전 GitHub 스냅샷: 커밋 `c0af0f1` (jaihaklee67/FallGuys_Sample)
- 새 Verse 파일은 `proto_` 접두사, 레벨 폴더는 `Test_Inheritance`, 기존 파일은 건드리지 않는다.
- 삭제 순서: 레벨 액터 → proto Verse 파일 → 새 에셋 → BuildAll → 스냅샷과 비교
- `Run Fix-up`은 Claude에게 알리지 않고 누르지 않는다. 코드만 바꿀 때는 `Push Verse Only` (F6) 사용.
- 편집 가능 칸(`@editable`)은 자식(구체) 클래스에 둔다. 칸을 다른 클래스로 옮기면 연결이 초기화된다.
- 커스텀 Verse 장치 참조 연결은 `<액터 경로>.<클래스명>_0` 경로를 쓴다.
